# AgentForge V4.0 — Deterministic Governance Control Plane (Developer Preview)

**Status: V4.0 control-plane implementation and offline tests, NOT a stable release.**

## 1. Architecture

The 4.0 increment deliberately does not alter the established V2.0 execution
pipeline by default. The V3.0 optional modules P0–P4.1 remain independently
installable; V4 consumes the **trusted V2 execution profile**, generates a
bounded execution proposal, verifies independent evidence from V3, and records
human approval through a protected audit chain.

```text
Request + repository + trusted execution profile
        |
        v
V4.0 Adapter Discovery (Django / Spring Boot / Vite / Node / Python)
        |
        v
V4.0 Deterministic Scope / Risk / Budget Admission
        |
        +---- BLOCKED (fail-closed)
        +---- AWAITING_HUMAN_APPROVAL (HMAC-bounded to commit/run/profile)
        +---- SCOPE_PRECHECK_OK (proposal only)
        |
        v
V4.0 DAG Wave Planner (stable ordering; parallel conflicts blocked)
        |
        v
OPTIONAL existing AgentForge V2/V3 execution outside this module
        |
        v
V3 P1 independent evidence + V3 P2 live canary verification
        |
        v
V4.0 HMAC audit journal (no automatic merging or deployment)
```

## 2. Modules

| Path | Function |
|---|---|
| `src/agentforge/v4/core.py` | Canonical paths, trusted V2 profile, budget admission, stack recognition |
| `src/agentforge/v4/scheduler.py` | DAG task waves with deterministic concurrency and conflict checks |
| `src/agentforge/v4/approval.py` | Explicit human approval token: run+task+commit+profile+request digest + expiry |
| `src/agentforge/v4/journal.py` | Bounded append-only HMAC journal with single-writer lock and state transitions |
| `src/agentforge/v4/budget.py` | Fail-closed cap checks against operator-provided usage counters |
| `src/agentforge/v4/bridge.py` | Re-verify signed V3 P1 evidence and actual V3 P2 opt-in proof |
| `src/agentforge/v4/release.py` | Advisory maturity checks; always forbids automatic merge/release |
| `src/agentforge/v4/cli.py` | Operator CLI that cannot write business source or execute models |
| `scripts/v4_acceptance.py` | Explicitly invoked offline pytest/protocol runner; NO LLM runs |

## 3. Safety invariants

1. **Trusted profile wins**: tasks contain no `write_scope`, `deny_scope`,
   `allowed_executables` or dynamic policy fields. V4 accepts only strict
   path and profile syntax and performs a conservative *subset* test. Actual
   execution **must** still pass through the existing V2.0 policy engine.
2. **No dynamic shell commands**: adapter verification argv are recommendations
   and V4 never executes them. The separate offline acceptance script runs
   only its fixed pytest and protocol verification commands when invoked.
3. **Stop means stop**: operator-created `.agent/v4/KILL_SWITCH` prevents any
   new admissions. To re-enable, a human must inspect the incident and remove it.
4. **Approval does not grant permissions**: operator-only HMAC token valid for
   one canonical request/profile/commit/run/task. TTL between 1 and 30 minutes.
   Token signing keys are supplied through environment, not repository files.
5. **Evidence is external to the Agent**: an LLM's own `SUCCESS` or `APPROVE`
   cannot produce V4 verified evidence. Synthetic three-round receipts are
   accepted only after the V3 independent verifier authenticates the P1 HMAC
   manifest and sees actual P2 mode. Historical 2/3 FAIL stays FAIL.
6. **Audit log cannot assert PASS via CLI**: only independently validated
   evidence can write `VERIFICATION_ATTESTED` through the verifier command.
   Free-text logs or tokens are never persisted in the audit trail.
7. **No production primitives**: no PR merge, deployment, direct DB mutations,
   autonomous model execution or auto-write entry points exist in V4.

## 4. Security / operational assumptions

- The repository's `.agent/execution-profiles.yaml` is reviewed and controlled
  by the maintainer, not generated by a model as an authorization source.
- Local audit authentication relies on an operator-controlled HMAC key and
  protected directory; HMAC chains detect modification, but cannot prevent an
  attacker who can restore an *old complete valid prefix*. External hash
  anchoring is required for tamper-evident retention across machines.
- Token file contains a bearer credential; store outside the repository with
  restricted permissions and short expiry. Never paste it into CI logs.
- The offline CLI validates a proposed plan only; it does not establish actual
  Python/Java/Node app correctness, operational safety, exactly-once credits,
  production throughput or real multi-project longevity.
- Budget checks take measured values from a caller. They are not authoritative
  until the values come from an independently authenticated execution host.
- Current V4 adapters detect frameworks and suggest commands; full Django
  migration, multi-tenant authorization, and service integration tests are
  future acceptance requirements, not implemented capabilities.

## 5. Release acceptance gate

A V4.0 **stable release** still requires all of:

- Existing V2.0 permission, fault-injection, Reviewer and multi-stack CI green.
- Python 3.11/3.12 each passing full test/protocol suite *three times* on the
  actual integrated branch commit.
- Three independent real DeepSeek rounds with P2 mode genuinely executed,
  four Agent successes, final Reviewer APPROVE, per-round 10 independent
  Node/Maven/Vite/MySQL/MySQL-concurrency gates.
- Independent P1 signatures bound to commit, run ID, model and full snapshots.
- Real Spring service-layer double-credit idempotency behavior checked.
- Separate Django read-only, API regression and database safety behavior tests.
- Maintainer inspection/approval. **No automatic production deployment.**

Until all these are proved with new GitHub run links, the correct status is
`V4.0 DEVELOPER PREVIEW — NOT RELEASE READY`.
